# TRADEINTEL AI

> **Trade Data Intelligence · Public Research · Supervised Communication**
> Built for **Voyage International Business** — Krakow, Poland (HQ) / Bengaluru, India (Procurement Hub)

---

## What TRADEINTEL AI Does

TRADEINTEL AI is **NOT** an autonomous sales agent. It provides an evidence-based intelligence and supervised outreach workflow that:

1. **UPLOADS DATA** — Ingests CSV / XLSX / XLS / JSON trade records.
2. **ANALYZES** — Extracts products, companies, markets and computes the 8-factor Customer Potential score.
3. **RESEARCHES** — Performs public web intelligence on relevant companies, products and markets.
4. **FINDS CONTACTS** — Discovers public contact candidates for human verification (with suppression checks).
5. **DRAFTS EMAILS** — Personalizes the Voyage International Business outreach template from persisted company and contact evidence.
6. **VALIDATES** — Verifies email format, suppression list and prior context.
7. **APPROVES** — Requires explicit human approval before any send.
8. **SENDS** — Sends approved messages through configured Hostinger SMTP and records SMTP acceptance (not delivery).
9. **MONITORS INBOX** — Polls Hostinger IMAP for replies.
10. **UNDERSTANDS REPLIES** — Classifies intent into 16 categories (INTERESTED, QUOTE_REQUEST, etc.).
11. **DRAFTS RESPONSES** — Creates intent-based reply templates for human review; replies are not generated by a live language model.
12. **FOLLOWS UP** — INITIAL → WAIT → FOLLOW-UP 1 → WAIT → FOLLOW-UP 2 → STOP (auto-stops on reply).
13. **DETECTS INTENT** — Identifies qualified leads from real commercial signals only.
14. **INFORMS HUMAN** — Surfaces leads for human review with evidence and recommended action.

## Architecture

### Stack
- **Frontend:** Vite + React 19 + TypeScript + Tailwind CSS v4
- **Backend:** Vercel Serverless Functions (`/api/*` directory)
- **Database:** Managed PostgreSQL accessed by the server-side `pg` client
- **Email:** Nodemailer (SMTP) + ImapFlow (IMAP)
- **Data Parsing:** SheetJS (xlsx) + native CSV/JSON parsers
- **Auth:** Supabase Auth (Email/Password + Google OAuth)

### Workflow Components
The application connects data import and analysis, public research, contact discovery, supervised outreach, inbox processing, response drafting, follow-ups, and CRM records. External-provider stages require their respective configuration and have not been verified against live services in this repository.

**Supervisor Orchestrator** — Coordinates `DATA → ANALYSIS → RESEARCH → CONTACT → EMAIL → HOSTINGER → INBOX → RESPONSE → FOLLOW-UP → INTENT → LEAD` pipeline.

## 8-Factor Customer Potential Algorithm

| # | Factor | Weight |
|---|--------|--------|
| 1 | Product Fit | 20% |
| 2 | Activity | 15% |
| 3 | Recency | 15% |
| 4 | Market Fit | 10% |
| 5 | Commercial Relevance | 15% |
| 6 | Growth | 10% |
| 7 | Supplier Diversification | 5% |
| 8 | Engagement/Intent | 10% |

**Categories:** `VERY_HIGH` (≥80), `HIGH` (≥65), `MEDIUM` (≥50), `LOW` (<50), `INSUFFICIENT_DATA`

---

## Reply Intent Classification (14 types)

`INTERESTED`, `PRICE_REQUEST`, `QUOTE_REQUEST`, `PRODUCT_REQUEST`, `CATALOG_REQUEST`, `SAMPLE_REQUEST`, `MEETING_REQUEST`, `NEGOTIATION`, `QUESTION`, `FOLLOW_UP_REQUIRED`, `NOT_INTERESTED`, `UNSUBSCRIBE`, `COMPLAINT`, `WRONG_RECIPIENT`, `OUT_OF_OFFICE`, `UNKNOWN`

---

## Response Draft Approval

Generated response drafts remain pending until a human approves them. Every reply send requires explicit approval; autonomous reply sending is unavailable. Commercial commitments (price, quote, negotiation) require human review.

---

## Follow-up Cadence

```
INITIAL → WAIT (3 days) → FOLLOW-UP 1 → WAIT (4 days) → FOLLOW-UP 2 → STOP
```

Auto-stop conditions:
- Reply received from prospect
- Bounce detected
- Unsubscribe / suppression triggered
- Lead already converted
- Human intervened

---

## Email Status Lifecycle

`DRAFT` → `GENERATED` → `VALIDATING` → `APPROVAL_REQUIRED` → `APPROVED` → `QUEUED` → `SENDING` → `SENT` → `REPLIED` / `NO_RESPONSE` → `FOLLOW_UP_DUE` → `COMPLETED`

Failed sends are tracked as `FAILED` with the real server error.

## Database Schema (Managed PostgreSQL)

- `datasets` — Uploaded trade files
- `raw_records` / `normalized_records` — Original and cleaned rows
- `companies` / `products` / `markets` — Extracted intelligence
- `company_potential` — 8-factor scores
- `web_research` — Public intelligence records (verification, confidence, source URL)
- `contacts` — Verified public contacts (with suppression flag)
- `outreach_emails` — Generated / sent emails (status, hostinger confirmation)
- `inbox_messages` — IMAP-synced replies (intent, extracted entities)
- `response_drafts` — AI-drafted replies (mode, review reasons)
- `follow_up_queue` — Cadence engine (waiting/sent/stopped)
- `leads` — Qualified leads (intent, score, evidence, recommended action)
- `crm_activities` — CRM timeline
- `agent_runs` — Supervisor execution history
- `audit_logs` — Admin and system action log
- `system_settings` — Hostinger config, sending limits, approval mode

---

## Security & RBAC

- All Hostinger SMTP/IMAP credentials are stored **server-side only** (in `system_settings` table or environment variables).
- **Never** committed to source, frontend, or localStorage.
- Authentication via Supabase Auth (email/password + Google).
- Admin / User roles enforced by the API using Supabase `app_metadata`.
- Grant the first administrator `app_metadata.role = "admin"` from a trusted server or Supabase admin tooling; never grant roles through client-controlled user metadata.
- Audit logging on every dataset upload, research action, email approval, Hostinger send, lead creation, and admin action.

## Local Setup

Create `.env.local` from `.env.example` only if it does not already exist. If it exists, add missing keys without overwriting its current values. Keep all environment files out of source control.

```powershell
# 1. Install dependencies
npm.cmd install

# 2. Configure DATABASE_URL (pooled PostgreSQL), optional DATABASE_DIRECT_URL
#    (preferred for migrations), and Supabase Auth frontend variables.
#    The migration runner loads .env.local automatically.

# 3. Apply the ordered, repeatable PostgreSQL migrations
npm.cmd run db:migrate

# 4. Run the Vite frontend only (the /api routes will not execute)
npm.cmd run dev

# 5. Run frontend + Vercel serverless functions locally (requires a linked Vercel project)
npm.cmd run dev:fullstack -- --listen 0.0.0.0:3000

# 6. Build production bundle
npm.cmd run build

# Optional: run a tagged synthetic PostgreSQL fixture that verifies and removes
# its own rows before committing. Use only a database where test writes are allowed.
$env:DATABASE_TEST_CONFIRM = 'CREATE_AND_DELETE_TEST_DATA'
npm.cmd run db:smoke
Remove-Item Env:DATABASE_TEST_CONFIRM

# 7. Deploy to Vercel only when intentionally publishing
# Configure environment variables in Vercel Project Settings.
```

The PostgreSQL database and Supabase Auth are separate services. Do not put database credentials or SMTP credentials in `vercel.json` or client-side `VITE_*` settings.

## Strict Operating Rules (Enforced Everywhere)

✅ **Allowed:** Understands · Researches · Analyzes · Contacts · Communicates · Listens · Understands · Responds · Follows Up · Identifies Intent · **Informs Human**

❌ **Forbidden:** Autonomous selling, negotiating, closing deals, accepting orders, promising delivery, signing contracts, making commercial commitments.

✅ **Honest Empty States:** `NO BUSINESS DATA AVAILABLE — UPLOAD DATA`. Never fabricates.

✅ **Honest Service Status:** Unconfigured external service shows `NOT CONFIGURED`, never simulated success.

✅ **Test Data Isolation:** Use Admin → Danger Zone → Purge before deploying real datasets.
